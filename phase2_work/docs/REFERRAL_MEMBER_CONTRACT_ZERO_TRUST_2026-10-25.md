# Member referral contract and Zero-Trust design — #48 (2026-10-25)

Status: existing contract defect corrected; lifecycle below is a **design proposal, not implemented or approved for rewards**. #48/#47/#55/#57/#8 remain OPEN. Production NO-GO. Base: main c5c4ec5dc323d13213643a090460a41cf5bad981.

## Current code and compatible correction

GET /api/referral authenticates the caller, derives a deterministic secret-key HMAC code, stores referralCode and returns {code,shareUrl}. referralCodeFor uses the first ten characters of uppercased Base64url, whose alphabet includes "-" and "_". POST /api/referral/claim previously accepted only A–Z and digits; some links generated by the server could never reach owner lookup. The validator now accepts exactly ten A–Z/digit/underscore/hyphen characters after the existing trim/uppercase normalization. No HMAC format, secret, code, storage schema or existing share URL is changed.

The claim still resolves a stored inviter code, rejects self-referral and records referredBy/referral_events attribution transactionally. Existing {ok:true} behavior includes an already-attributed no-op; it does not attest identity, qualification, delivery of a benefit or entitlement. Referral codes are opaque routing identifiers, not authorization credentials. Accepting their actual alphabet does not authorize arbitrary UIDs or mint rewards. Invalid lengths, Unicode, path separators and punctuation remain rejected before owner lookup. Authentication and UID-scoped distributed limits remain in place.

This patch does not repair other lifecycle gaps: generation currently writes referralCode with merge, and the claim path is not the full deletion/age/consent/expiry/rotation state machine proposed below. Account resurrection/deletion-marker handling needs a separately tested transaction change; do not claim that this proposal is already enforced.

## Separate actors and trust boundaries

| Actor / source | Permitted authority | Must never authorize |
| --- | --- | --- |
| Inviter | Request/copy a personal invitation for their own eligible account | Badge, invitee identity, self-qualified reward |
| Invitee | Authenticated explicit claim of one invitation | Supplying another buyer/account UID, replacing a prior claim |
| Signed, session-bound Didit processing | Current identity/KYC result under existing server checks | Reward fulfillment or partner purchase proof |
| Activation analytics / client events | Non-authoritative measurement | KYC, qualification, entitlements |
| B2B partner webhook | Signed partner assertion placed in reconciliation/quarantine | Independent purchase proof, member-referral reward |
| Future reward ledger / entitlement adapter | Only approved server events and verified fulfillment receipts | Client/partner self-reported success or duplicate credit |

B2B /api/partner/* contracts remain distinct from member /api/referral and /api/referral/claim. Existing partner consent does not silently authorize member tracking or vice versa.

## Proposed lifecycle and invariants

issued → visited → registered → verified → qualified → rewarded, with revoked/expired/rejected terminal rejection states and a separately auditable reversal of fulfilled benefits. A crawler visit must never qualify or reward; visited is optional, consent-dependent measurement. Registered is an authenticated explicit claim, not a page load. Verified derives only from current authoritative Didit state, not activation or invitation metadata.

Every transition must pin invitation ID, inviter/invitee account IDs internally, purpose/schema version, current consent epochs, eligibility-policy revision, expiry and immutable source event ID. Recheck both accounts, their deletion markers, age/consent/quarantine status and prior claim inside the transaction. Enforce one qualifying inviter per invitee and one benefit per approved source event through transactional uniqueness records, not a read followed by independent writes. A conflict is explicit, not silently reassigned. No raw UID/email in public URLs or partner links.

Persist enough minimal signed evidence for retry and reconciliation; do not persist raw ID documents or an unbounded client metadata blob. Secret versions and token purposes must be explicit before introducing rotation/short-lived invitation tokens. Define overlap and expiry before migration; do not invalidate existing links by replacing the HMAC encoder during this bugfix.

No reward type, duration, cap or financing is approved. Klar+ periods remain a possible product decision, never an enabled benefit. Qualification and fulfillment must be separate; retries use stable event/ledger keys; refund, fraud, chargeback and revocation require an approved policy and append-only reversal evidence. Invitations cannot grant KYC badges, coins, paywall bypass, VIP status or unapproved duration.

## Migration and acceptance plan

1. Preserve current response shapes and existing code lookup. Deploy the alphabet compatibility fix first.
2. Before lifecycle writes: settle member consent/legal basis, retention/holds and deletion semantics; add safe existing-account/deletion gates and protect already-claimed attribution. Do not activate rewards.
3. Introduce versioned records in shadow validation with explicit legacy mapping. Legacy attributed does not imply verified/qualified/rewarded. Any backfill requires inventory, dry run and approval for affected data.
4. Emulator and HTTP/E2E tests must cover concurrent claim, duplicate verification, different inviter, self-referral, missing account, deletion before/during transaction, revoked/expired code, missing/withdrawn consent, KYC failure and webhook retries. Reward tests additionally need verified fulfillment, cap, refund/reversal and idempotent reconciliation; none of those are asserted complete here.
5. Release only with exact-head CI, actual staging receipts, independently authorized privacy/security review and product terms. Technical contact is @Veselin-Takev; independent approvers are not assigned by this document.

## Evidence for this patch

Twenty local tests PASS across launchEndpoint.spec.ts and launchPlatform.test.ts under Node 24.22.1 / Vitest 5.0.5. A new HTTP regression takes a code generated by the actual production helper containing "-" or "_", submits its lowercased form and proves it reaches stored owner lookup rather than malformed-code rejection. Six invalid-format cases are rejected before user lookup. Tests use loopback HTTP and an isolated Firestore FieldValue adapter; no emulator, production, KYC or reward proof is claimed. Full pinned-runtime CI on the published head remains required.

Rollback of this validator alone would make some existing generated links unusable again. Do not rotate secrets, rewrite stored codes or delete attribution records as a rollback shortcut.
