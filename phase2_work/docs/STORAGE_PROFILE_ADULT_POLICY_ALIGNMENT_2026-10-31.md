# P1 #204 – Adult-Policy-Drift in Cloud Storage Profilbild-Regeln

**Stand:** 31.10.2026 · **Status:** DRAFT / BLOCKED / NO-GO · **Independent base:** unverändertes `main` SHA `2808dc1cbb485f70b403681c108cea5a3361d950` · **Issue:** [#204](https://github.com/Veselin-Takev/Klar-Dating/issues/204).

## Nachgewiesener Quellbefund

`storage.rules` enthielt für `/profiles/{uid}/{datei}` zuvor `allow read: if signedIn();`. Darauf konnte ein angemeldetes, aber nicht nachweisbar volljähriges Konto zugreifen. `storageRulesEngine.ts` enthielt bereits eine deutlich strengere *nur modellierte* Policy, wonach auch der Profileigentümer volljährig sein muss. Das Storage-Emulator-Testinventar prüfte die maßgebliche Kombination nicht vollständig. Der Zustand ist eine **source-level Berechtigungsabweichung**, kein Beleg für eine reale Cloud-Datenabfrage oder einen eingetretenen Datenschutzvorfall.

## Implementierte begrenzte Korrektur

- `storage.rules` benutzt den **serverseitig gespeicherten** Status `users/{uid}.isAdult == true` über `firestore.get(...)`, nicht das vom Client angebbare Geburtsdatum oder möglicherweise veraltete JWT-Age-Claims. Das Quell-Firestore-Regelwerk verweigert Client-Erstellung und -Änderung von `isAdult`; serverseitige Autorisierung bleibt Pflicht.
- Leser müssen authentifiziert, nicht anonym und laut `users/{auth.uid}.isAdult` volljährig sein; für **Profil-Lesen** wird zusätzlich `users/{uid}.isAdult` verlangt. Uploads und Löschungen erfordern das serverseitige Volljährigkeits-Gate sowie eigene UID. Biometrische `verification/`-Dateien bleiben **für alle Clients unlesbar**, Delete bleibt server-only. Das bereits erlaubte Verification-Upload-Verhalten wird um die Adult-Bedingung eingeschränkt, jedoch **nicht** für neue Berechtigungen geöffnet.
- Das rein logische `storageRulesEngine.ts`-Modell erfordert statt `auth.token.isAdult` ein **server-abgeleitetes** `requesterUserIsAdult` und für Profil-Lesezugriffe `targetUserIsAdult`. Unbekannte oder fehlende Werte schlagen **fail-closed** fehl.
- `tests/storageRules.spec.ts` bereitet mit `firebase.rules-unit-testing` echte **lokale** Firestore-Benutzerdokumente vor und testet über den Storage Emulator angemeldete Adult/Minor/Unknown/Ano­n­ymous-/Gast-Kombinationen sowie Upload/Read/Delete. Die Testausführung verweigert den Storage-Kontext ohne passenden lokal konfigurierten Firestore Emulator, Projekt `demo-klar` und nichtproduktive Laufzeit.
- `tests/enterprise/storageSecurityRules.spec.ts` überprüft das logische Modell einschließlich unbekannter Age-Claims. `scripts/check-storage-age-gate.mjs` ist jetzt Teil von `check:enterprise`; sieben Mutationstests erkennen entfernte Adult-/Owner-Gates, unzulässige zweite Read-Regeln und den Rückfall auf eine bloße JWT-Age-Angabe.

## Notwendige Grenzen und Vorabentscheidungen

1. **Maximal zwei Firestore-Dokumente:** Cloud Storage Security Rules können pro Auswertung nur auf **zwei** Firestore-Dokumente zugreifen. Beide sind hier für Leser und Profilinhaber verbraucht; Blocklisten, laufende Kontolöschungen und feinere Sichtbarkeitspräferenzen können nicht einfach mit weiteren `firestore.exists`-Abfragen ergänzt werden. Endgültige Produkt-Policy braucht deshalb einen **serverseitig authentifizierten, widerrufbaren Bildlesepfad** mit serverkontrollierter Freigabe und Block-/Erasure-Prüfungen. Produkt, Security und Datenschutz/Legal müssen dies bestätigen. Quelle: https://firebase.google.com/docs/storage/security/rules-conditions
2. **Langlebige URL-Capabilities aus #206:** `getDownloadURL` erzeugte bereits zuvor teilbare `?token=`-Links. Diese URLs sind **nicht durch neue Firebase Storage Rules zurückgerufen** und können von Empfängern unter Umgehung des SDK-Regelchecks weiter genutzt werden. Keine Aussage über eine tatsächlich gelungene Token-Sperrung. [P1 #206](https://github.com/Veselin-Takev/Klar-Dating/issues/206) bleibt separat offen.
3. **Cross-Service-IAM und Kosten:** Die neuen `firestore.get`-Prüfungen benötigen die Google Cloud IAM-Berechtigung für Cloud Storage Rules → Firestore in der **Default-Datenbank**. Ohne diese externe Konfiguration versagt der Pfad möglicherweise ganz (fail-closed). Relevante Firestore-Lesevorgänge sind kostenpflichtig. Projekt-/Dienstkonto-/Ruleset-/Bucket-/Firestore-Datenbankidentität muss durch SRE in Staging/Produktion nachgewiesen werden; keine IAM-Änderung ist in dieser PR vorgesehen.
4. **Backward compatibility / Rollback:** Fehlende `isAdult`-Felder und ältere Accounts verlieren bewusst Zugriff und Upload-/Delete-Berechtigungen bis zur serverseitigen Altersbestätigung. Produkt und Support müssen das sicher kommunizieren; ein Rollback auf `allow read: if signedIn();` würde die Sicherheitslücke erneut öffnen und ist als Sicherheitsmaßnahmen ungeeignet. Kontolöschung über Admin SDK bleibt separat.
5. **Test-Evidenz:** Ein vollständiger CI-PASS auf dem exakten neuen SHA (Enterprise Gates, TypeScript, Functions, Storage+Firestore Emulator, Build, Browser-Abnahme) ist für eine technische Prüfung obligatorisch. Emulator-Beobachtungen beweisen **keine** ausgerollten Regeln, reale IAM-/Storage-Projektbindungen, historische Downloadlink-Widerrufe, Drittanbieter-Caching oder betroffene Live-Nutzer. Unabhängige AppSec/DPO/Legal/SRE/Release Owner-Freigaben fehlen.
