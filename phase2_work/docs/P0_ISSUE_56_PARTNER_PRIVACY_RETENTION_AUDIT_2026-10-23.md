## 2. Classified remaining blockers (do not invent deployed failures)

| ID | Observation or unmet decision | Class / remedy |
| --- | --- | --- |
| `P56-01` | `klar_referral` deliberately reaches the third-party destination even with `Referrer-Policy:no-referrer`. External possession, browser/partner log retention and onward sharing cannot be controlled only by Klar. | **Confirmed privacy trust-boundary exposure by design; legality and deployed leakage extent unverified.** Decide whether short-lived one-time exchange-token + authenticated server-side attribution can minimize scope; separately contract third-party retention, recipient notifications and user rights. |
| `P56-02` | Inspected consent write stores boolean/epoch/time and signs event; no explicit immutable `consentNoticeVersion`/`legalBasisVersion`/purpose text reference is visible in that write path. | **Evidence-schema gap, not a definitive violation.** DPO must evaluate full end-to-end consent evidence and specific, informed, freely given purpose; preserve provenance of exact notice, locale, time and withdrawal without over-retention. |
| `P56-03` | Deterministic token identifies an epoch and owner/campaign to Klar; after disclosure, third party may retain token although future Klar clicks/conversions are denied on epoch mismatch. | **Revocation boundary**. Test local suppression; require partner deletion/expiration and contractual withdrawal propagation for previously exported data; do not promise retroactive deletion already performed. |
| `P56-04` | Partner events, conversions and signed ledger are HMAC-pseudonymous and potentially re-linkable with secret + account; ledger is not anonymous merely because UID plaintext is absent. | **Data classification/retention decision**. Inventory recipient, linkability, backup/restoration and HMAC key rotation effects on Art.17. Legal holds require legal assessment and narrow documented grounds. |
| `P56-05` | `DATA_RETENTION.md` has old sections saying **13 required ACTIVE groups** plus a later amendment requiring a signed **20-group matrix**. | **Confirmed documentation/version drift.** Current source revision is 20-group pending independent approval. Replace 13-group operating instructions **only after** approved 20-group change; never claim 13/13 or 20/20 live PASS. No Cloud TTL changes are authorized. |
| `P56-06` | Account-erasure code has sophisticated quarantine and pseudonymous cross-party sweeps but production-grade emulator transaction tests and external partner processor/recipient cleanup evidence were not supplied. | **Unverified operational control, not proof of a bug.** Test owner/buyer interleavings, many-page scans, resume/lease, external token reuse, orphan ledger and account recreation across rotation epochs. |
| `P56-07` | Paid proof/settlement and refunds remain open under #55/#57. Financial retention may have competing legal duties. | **Legal/Finance dependency.** Define per-entity processing purpose, legitimate retention schedule, exception and documented disposition. Never apply indiscriminate TTL to relevant financial evidence. |
| `P56-08` | Public and private route response headers are set in source, but deployed reverse proxy, partner destinations, tokens in history/logs and international transfers were not tested. | **Environment/contract evidence missing.** Require staging browser/proxy header observations, privacy impact and partner DPA/terms reviews; no hypothetical cross-border transfer is asserted as observed. |

## 3. Data-inventory and retention decision worksheet — NO defaults invented

For every collection, the DPO + Legal + Finance (as appropriate) must record: purpose, lawful basis, data fields, controller/processor/recipient, identifiable vs pseudonymous, source, creation/update and TTL timestamp semantics, approved period and trigger, legal hold rules, DSAR/erasure/export route, third-party deletion contract, audit evidence and signer. No unspecified retention number becomes policy merely by appearing in draft paperwork.

| Dataset | Linkage | Disposal and rights evidence required |
| --- | --- | --- |
| `users.partnerReferralConsent`, `partnerReferralVersion`, update timestamp | Direct user UID | Withdrawal, audit of proof, account deletion, legitimate retention exception |
| `partner_referrals` | Owner UID / campaign / epoch, token-derived ID | Live consent and revocation, owner deletion, no stale token acceptance |
| `partner_referral_conversions` | HMAC owner/buyer refs, event/campaign/referral IDs | Erasure of either party, purchase proof status, reconciliation and duplicates |
| `partner_referral_buyer_claims` | HMAC buyer ref plus referral ID | Owner/buyer deletion, cross-buyer sweeps, parallel claim races |
| `partner_referral_ledger` | HMAC actor/owner/buyer refs, signed consent/campaign/click/conversion events | Signed audit, immutable evidence disposition, justified hold if any |
| `partner_campaigns`, `partner_campaign_slugs` | Campaign + HMAC admin references | Legal business-record retention vs linked human admins, scrub and external agreements |
| Four `partner_referral_*_rate_limits` groups | Hashed IP, UID or campaign-keyed counters; `expiresAt` | TTL field type/period, live ACTIVE and suppression, no unnecessary key retention |
| Third-party URL, analytics, advertising/partner logs | Forwarded `klar_referral` + partner context and possible browser identifiers | Full recipients, lawful basis, erasure/withdrawal message, link expiry, international transfers |
| Approved financial or dispute holds | Potentially linkable transaction and consent evidence | Statutory/contract-specific scope, access isolation, review date and erasure after hold ends |

## 4. Exact acceptance tests (proposed, NOT EXECUTED)

| Scenario | Fail-closed assertion | Environment |
| --- | --- | --- |
| Partner toggle off before link issuance | No new personalized link or audit tracking, no change to Free base features | UI + API + Firestore emulator |
| Visitor click without independent valid opt-in | Redirect only to permitted **untracked** destination, no counted click, no visitor ledger | Browser/proxy + emulator |
| Withdraw then replay old link | Token epoch mismatch suppresses new attribution; verify what still appears in external partner logs | Browser/partner sandbox + emulator |
| Withdraw and immediately regrant | Regranted new epoch cannot revive earlier token or pending conversion; stale callbacks fail | Real concurrent emulator |
| Withdraw during counted-click transaction | Commit conflicts/re-checks current owner + visitor epochs; no unauthorized ledger | Real Firestore emulator |
| Pseudonym/secret rotation with pending erasure | Every old and new pseudonymous reference discoverable and disposed via approved migration mapping | Deletion emulator + key management |
| Erase referrer owning many buyer claims | Quarantine before claim purge; no late claims; all owned referrals, linked claims, conversion and ledger refs removed | Paginated concurrent emulator |
| Erase buyer with active claim/pending conversion | Buyer claim, conversion, ledger and related buyer references deleted as policy requires | Real Firestore emulator |
| Interrupted deletion after quarantine | Restart idempotently, preserve deletion tombstone and no orphaned dependent records | Emulator/resume |
| Existing legal hold and expired TTL timestamp | No unapproved auto-deletion; allow legally mandated scoped hold handling only | Retention simulator/staging evidence |
| Expected 20 versus unexpected group policy | Validator rejects any extra, wrong, missing, altered or non-ACTIVE TTL policy | Staging read-only + signed reviewer evidence |
| Public and private responses | Effective `Cache-Control`/`Referrer-Policy` through actual ingress; no raw token in nonessential analytics/logs | Staging browser/proxy |
| DSAR/export and privacy text localization | Scope includes partner profiles, click/claim history, HMAC refs and recipients; DE/EN/ES/FR accurate | User E2E + Legal review |
| Independent partner deletion/notice and international transfer | Signed partner response/contract plus deletion and transfer assessment | DPO/Legal plus controlled partner validation |

Existing fake-Firestore tests in `tests/partnerReferralService.spec.ts` cover consent epochs, stale links and some click races in **mock source**; the actual execution and production integration evidence are not present. Do not infer full Art.17 or GDPR certification from test names.

## 5. Release sequencing and signoffs

1. **DPO/Legal (#56):** Sign processing record (purposes, lawful bases, recipient/processor roles, DPIA screening), actual consent wording/proof and external partner/token/erasure agreements. Clarify privacy notices, withdrawal rights, international transfers and retention exceptions. Under GDPR, pseudonymous but linkable data remain in scope.
2. **Product/Security (#55, #48):** Retain signed-conversion quarantine. Approve minimization of persistent partner URL tokens and independent buyer-to-order intent. Keep B2B partner controls separate from member invitation rewards.
3. **DPO/Legal/SRE (#70):** Authorize a full, versioned **20-group** retention/hold policy, source/schema inventory, exact staging project+database, no unexpected policies and independent evidence, before any TTL apply. Old 13-group text is a known legacy instruction, not permission for release.
4. **Engineering/QA (after formal audit unlock):** Add approved data-schema changes on isolated feature branch, run genuine transaction, key-rotation, DSAR, privacy headers, consent-withdrawal and deletion tests using pinned toolchain, then full exact-SHA CI; separate real external partner sandbox evidence.
5. **SRE/Release Owner (#8, #73):** Validate effective CODEOWNERS/permissions, actual runner and production controls, rollback, alert delivery and all authenticated host-gate receipts. Require independent formal Security, Privacy, Legal, Operations and Release Owner approvals.

**No test execution, Cloud listing, TTL mutation, code patch, incident recovery, merge, deployment or GO is authorized by this report.** Pending evidence must be delivered through approved private channels with original bytes, checksums, signer identity, environment and exact SHA. Sensitive buyer data/secrets must not enter public GitHub documentation.
