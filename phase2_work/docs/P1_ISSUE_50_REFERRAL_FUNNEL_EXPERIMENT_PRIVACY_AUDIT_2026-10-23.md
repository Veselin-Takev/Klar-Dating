## 3. Proposed event dictionary (DESIGN ONLY — NOT IMPLEMENTED)

Each measurement row requires a signed owner, `schemaVersion`, stable server-generated `eventId`, `createdAt` server timestamp, `environment`, `campaignPolicyVersion`, source/provenance status, dedup key, lawful purpose, approved expiry and minimal pseudonymous correlation. Never expose raw UIDs, referral graph, provider payload, personal interests, relationship intent, photos, IP, biometric records or private message content to external analytics.

| Proposed event | Authority | Safe interpretation and exclusion |
| --- | --- | --- |
| `member_invitation_issued` | Klar server member-invite issuance transaction | A valid issued token, not delivered; no grant or conversion. |
| `member_invitation_share_initiated` | Consented client UX signal | Voluntary action only; clipboard counts as copied, not delivered. Respect opt-out and one-shot cancellation. |
| `member_invitation_delivered` | **Not currently evidenced**. Only if an independently legitimate delivery receipt exists (e.g. approved optional first-party channel) | Do **not** emulate from share API success, email self-report or external pixel. Without lawful proof, primary delivered-invitation KPI remains not measurable. |
| `member_invitation_visited` | Server first-party landing event after bot/preview filtering and eligible privacy basis | Visit is not a person, a registration or genuine qualification. |
| `member_invitation_registered` | Firebase Admin verified UID/account creation + server-owned canonical claim transaction | One invitee attribution, self-referral/conflicts excluded; absence of legal basis forbids marketing export. |
| `member_invitation_kyc_approved` | Signed Didit decision linked to the same account/session, up-to-date nonrevoked | Only provider-backed KYC proof; isolate from client `biometrics_success`. |
| `member_invitation_qualified` | Independent server-owned policy + fraud/age/consent gates, durable idempotent transition | Not an activation event from POST body. |
| `member_klarplus_duration_granted` | Authorized immutable entitlement ledger with actual finite start/end + grant ID | Actual benefit receipt only; source `BUCHBAR=false` and absent reward flow mean this is **not currently delivered**. |
| `member_klarplus_duration_reversed` | Authorized compensating ledger event, policy and signer | Real reversal only; do not overwrite original grant evidence. |
| `cohort_d7_active`, `cohort_d30_active` | Server-defined meaningful activity on approved eligible measurement window | Do not infer from client activation score or refreshed profile publish timestamp. |
| `verified_suggestions_served`, `zero_suggestions`, `recommendation_error` | Recommendation server outcome and eligibility, not client-reported generic click | Differentiate true low supply, genuine served suggestions and operational error. |
| `report_guardrail_aggregated` | Trust-and-Safety approved pseudonymous aggregate | Safely bucketed report/spam rate; never send private report details to marketing. |

**Privacy:** The existing `funnel_events` source contains direct `userId` and a hashed session, so it is **pseudonymous/linkable** within Klar and subject to approved GDPR processing and Art.17. The hash does not make the events anonymous. Any reporting aggregates need tested minimum-cell suppression and irreversible privacy transformation approved by DPO.

## 4. Pre-registered A/B/C pilot specification — pending approval

**No experiment is running or approved.** Scope would be **one approved city** with sufficiently usable, verified local supply (#51), no excessive marketing pressure, no artificial scarcity, no false KYC guarantee or nonexistent Klar+ incentive. Variants A/B/C must use truthful editable DE/EN/ES/FR copy and one shared default Free eligibility policy.

- **Unit of randomization:** inviter UID / eligible campaign cohort, **stable server-side assignment** before first exposure and immutable across sessions, with a signed policy and opt-out handling. Avoid assigning per request or causing repeated exposure to new variants. Account/household/device interference and social sharing between groups require planned spillover analysis.
- **Assignment integrity:** approve campaign version and experiment ID, traffic and country/city scope, stable cryptographic bucketing/holdout, tamper resistance, variation parity, retained minimal receipt and single source of exposure. An assignment alone is not an actual exposure.
- **Primary metric mandated by Issue #50:** `100 × unique independently verified-and-qualified invited users / independently observed delivered invitations`. At this SHA **both reliable denominator and qualifying state are missing**; display `NOT MEASURABLE`, never divide by share button taps. If lawful independent delivery proof is impractical, Product/DPO must *formally change metric definition* (e.g. per 100 server-issued invitations with separate recipient click qualification), not silently substitute.
- **Guardrails:** real D7/D30 retention, signed KYC completion, genuine eligible suggestions per user, report/block/spam/complaint rates, consent opt-out rates, user feedback, first-party Free journey, security/fraud and incremental CAC per verified *activated* user. Use same definitions and denominators across variants, stratify by sufficiently populated eligible city/age/intention cohorts without exposing sensitive data.
- **Statistics:** pre-register randomization and stop/continue rule, primary and guardrail test, baseline, sample-size/power calculation based on *observed* pilot data, alpha/multiplicity adjustment, clustered interference, duration and horizon, confidence intervals and inconclusive handling. **No statistical threshold, sample size, uplift, baseline or result is invented here.** Avoid repeatedly peeking and shipping on a lucky interim point.
- **Spending:** Finance sign-off on all marginal KYC attempts (including failed/retries), fraud/support, Cloud/AI/token costs, actual verified incremental conversions, refunded/net Klar+ contributions and approved upper liability of 0/7/30-day benefits. All paid reward variants remain disabled under #53.
- **Rollback:** explicitly authorized default-OFF feature flag, stop on elevated reporting, missing data, zero verified local supply, failed consent, weak KYC economics or platform failures; no deceptive UX or hidden core Free restriction. No backfilling absent lawful consent.
